勉強法実験アプリ
技術選定書 v1.0
1. 技術選定の基本方針
本プロジェクトでは、2週間という短い開発期間を考慮し、開発速度・実装難易度・安定性を重視する。
特に、以下の5点を優先する。
初心者でもAIコーディングを活用して開発できること。
複雑な環境構築を必要としないこと。
2人で並行して開発できること。
無料で開発・公開できること。
将来的な機能拡張に対応できること。
MVPではバックエンドを構築せず、フロントエンドのみで動作するWebアプリケーションを開発する。

3. フロントエンド
3.1 React
採用理由
Reactは、画面をコンポーネント単位で構築できるJavaScriptライブラリである。
本アプリでは、以下のような画面を実装する。
ホーム画面
実験設定画面
学習画面
確認テスト画面
結果画面
実験履歴画面
履歴詳細画面
Reactを採用することで、ボタン、カード、タイマー、問題表示などを再利用可能なコンポーネントとして実装できる。
また、AIコーディングでの実装例も豊富であり、開発を進めやすい。
3.2 TypeScript
採用理由
TypeScriptはJavaScriptに型の仕組みを追加した言語である。
本アプリでは、以下のようなデータを扱う。
勉強法
問題セット
実験情報
テスト回答
正答率
実験履歴
TypeScriptを使用することで、データ構造を明確にし、実装ミスを減らす。
特に2人で共同開発する際、データの形式を統一できる点がメリットとなる。
3.3 Vite
採用理由
Viteはフロントエンド開発用のビルドツールである。
ReactとTypeScriptを使用する開発環境を簡単に構築できる。
開発サーバーの起動が速く、コード変更後の画面確認もスムーズに行える。

4. UI・デザイン
4.1 Tailwind CSS
採用理由
Tailwind CSSを使用し、画面のデザインを実装する。
主な用途は以下のとおり。
レスポンシブデザイン
画面レイアウト
ボタンのデザイン
カード表示
余白や文字サイズの調整
CSSを一から大量に記述する必要がなく、AIコーディングとも相性がよい。
4.2 shadcn/ui
採用理由
ボタン、カード、ダイアログなどのUIコンポーネントを利用する。
本アプリでは、以下のコンポーネントを中心に使用する。
Button
Card
Progress
Dialog
Badge
ただし、MVPでは必要なコンポーネントのみ導入する。
導入や調整に時間がかかる場合は、Tailwind CSSによるシンプルな自作コンポーネントで代替する。

5.1 Recharts
採用理由
RechartsはReact向けのグラフライブラリである。
本アプリでは、勉強法ごとの正答率を比較するために使用する。
MVPで使用するグラフ
棒グラフ
2種類の勉強法の正答率を比較する。
例：
勉強法
正答率
書いて覚える
70%
思い出して覚える
90%

将来的な拡張
直後と翌日の正答率比較
複数回の実験結果の推移
勉強法ごとの平均正答率
MVPでは棒グラフのみ実装する。

6. データ保存
6.1 localStorage
採用理由
MVPではlocalStorageを採用する。
localStorageは、ブラウザ内にデータを保存する仕組みである。
バックエンドやデータベースを構築する必要がないため、開発時間を短縮できる。
保存するデータ
実験ID
実験日時
選択した勉強法
実験前の予想
使用した問題セット
学習時間
テスト回答
正答率
実験の進行状況
実装方針
localStorageへのアクセスは専用の関数にまとめる。
画面コンポーネントから直接保存処理を大量に記述しない。
これにより、将来的にSupabaseなどへ移行しやすくする。
注意点
データは端末・ブラウザごとに保存される。
ブラウザのデータ削除によって履歴が消える可能性がある。
異なる端末間での同期はできない。
保存データの形式が変更された場合に備え、バージョン番号を管理する。

7. 問題データ
7.1 JSON形式
英単語と日本語訳をJSON形式で管理する。
データ例
{
  "id": "word-001",
  "english": "apple",
  "japanese": "りんご",
  "level": 1
}

採用理由
データの追加・編集が簡単
サーバーを必要としない
TypeScriptから扱いやすい
将来的に問題登録機能へ拡張しやすい
問題セットの設計
MVPでは、難易度が近い英単語セットを複数用意する。
1セット10問とし、2種類の勉強法には異なるセットを割り当てる。
実験結果には、使用した問題セットのIDを保存する。

8. 画面遷移
8.1 React Router
採用理由
複数画面の遷移を管理するため、React Routerを使用する。
想定するルートは以下のとおり。
URL
画面
/
ホーム
/experiment/new
実験設定
/experiment/:id/study
学習
/experiment/:id/test
確認テスト
/experiment/:id/result
実験結果
/history
実験履歴
/history/:id
履歴詳細

実験の進行状況は保存データから取得する。
画面を再読み込みした場合も、保存済みの実験情報を参照できる構成にする。

9. バージョン管理・共同開発
9.1 GitHub
2人で同じリポジトリを使用する。
基本ルール
main：動作確認済みのコード
feature/xxx：機能開発用ブランチ
新しい機能を実装する際は、原則としてfeatureブランチを作成する。
実装完了後、Pull Requestを作成してmainに統合する。
開発時の注意点
同じファイルを同時に大きく編集しない。
1つのブランチでは、できるだけ1機能を実装する。
mainに統合する前に動作確認する。
AIが生成したコードも、動作を確認してから統合する。

10. デプロイ
10.1 Vercel
採用理由
GitHubのリポジトリと連携してWebアプリを公開できる。
主なメリットは以下のとおり。
GitHubとの連携が簡単
HTTPSに対応
React + Viteのアプリを公開できる
無料枠を利用できる
更新を反映しやすい
デプロイ方針
開発初期にVercelへデプロイする。
最終日まで公開作業を後回しにしない。
React Routerを使用する場合は、直接URLにアクセスしても画面が表示されるように、SPA向けのリライト設定を行う。

11. AIコーディングの活用
CodexなどのAIコーディングツールを使用する。
主な用途
Reactコンポーネントの実装
TypeScriptの型定義
localStorageの保存処理
テスト機能の実装
グラフ表示
エラー修正
コードレビュー
開発方針
AIには、一度にアプリ全体を実装させるのではなく、機能単位で実装を依頼する。
例：
勉強法選択画面を実装する。
動作確認する。
問題表示機能を実装する。
動作確認する。
タイマー機能を追加する。
小さな単位で実装と確認を繰り返す。

12. 採用しない技術
MVPでは、以下の技術を採用しない。
技術
理由
Next.js
今回はサーバー側の機能が不要
独自バックエンド
開発期間に対して実装負担が大きい
PostgreSQL
MVPでは本格的なデータベースが不要
Supabase
認証・クラウド保存は追加機能とする
AI API
結果コメントは条件分岐で実現可能
Docker
今回の構成では必須ではない

技術選定の結論
React + TypeScript + Viteを中心とした、バックエンド不要のWebアプリケーションを採用する。
MVPの完成を優先し、必要に応じて機能を追加できる構成とする。
